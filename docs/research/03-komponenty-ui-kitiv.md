# 03 · Базові компоненти UI-кітів

> Ресьорч до задачі 14, крок 4. На його основі на кроці 5 пишуться
> специфікації компонентів. Стан бібліотек — на листопад 2026.

## Рішення, ухвалені до ресьорчу

- **Обсяг** — увесь каталог одразу, без поділу на хвилі. Порядок
  реалізації — нижче, у розділі 6.
- **Основа** — Reka UI: headless-примітиви з готовою доступністю і
  клавіатурою. Візуальний шар, токени й API — наші.
- **Що потрапляє в кіт:** загальні компоненти, а також доменні компоненти
  Kite, які переходять із застосунку в застосунок. Робочий критерій — компонент
  потрібен **щонайменше двом** із kite-web, kite-business, kite-ops,
  kite-box-screen. Решта живе в застосунку.
- **Карта** (MapLibre) — окремий пакет `@kite-post/map`, не частина кіта.

## 3. Каталог `@kite-post/ui`

Колонка «Reka» — примітив, на якому будується компонент. «—» означає, що
компонент наш, без примітива (зазвичай нативний HTML). Колонка «Де» —
застосунки: **w** kite-web, **b** kite-business, **o** kite-ops, **x**
kite-box-screen.

Усі чотири потрібні щонайменше у двох застосунках, тому живуть у кіті.

карті (`@kite-post/map`).

| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Контекстне меню, шапка клієнтського сайту      | Кожен потрібен лише одному застосунку (меню — kite-ops, шапка — kite-web), тож живе в ньому. Контекстне меню kite-ops будується на `ContextMenu` з Reka і токенах кіта |
| Карта, вибір точки на карті                    | Окремий пакет `@kite-post/map` (важкий MapLibre не потрібен кожному застосунку)                                                                                        |
| Графіки (Chart)                                | Потрібні лише дашбордам b і o. Кандидат на окремий пакет, коли з'являться реальні дашборди                                                                             |
| Carousel                                       | Анти-патерн (не дочитують, погана доступність); маркетинг поза обсягом                                                                                                 |
| Rating, Color picker, Slider                   | Немає сценаріїв у Kite (слайдер для діапазону ціни — радше два NumberField)                                                                                            |
| Menubar, Hover card, Aspect ratio, Scroll area | Немає сценаріїв або вистачає CSS (`aspect-ratio`, нативна прокрутка)                                                                                                   |
| Tree, Splitter, Editable                       | Немає сценаріїв у MVP; Tree — Alpha                                                                                                                                    |
| Форм-бібліотека (валідація)                    | Кіт не прив'язується до VeeValidate чи іншої: `KField` приймає помилку пропсом, валідація — справа застосунку                                                          |
| Компоненти AI-асистента Kit                    | v2 і лише w; буде видно, коли з'явиться дизайн                                                                                                                         |
| Типографічні компоненти (`KHeading`, `KText`)  | Вистачає семантичних тегів і утилітних класів токенів; компонент заради стилю — зайвий шар                                                                             |

## 5. Ризики

1. **Alpha-примітиви Reka UI 2.11:** уся група дат (`DatePicker`,
   `DateRangePicker`, `Calendar`), `Drawer`, `Field`, `Autocomplete`. API може
   змінитися в мінорному релізі.
   - Версію Reka закріплюємо точно (`2.11.x`, без `^`) і оновлюємо осмислено.
   - Наші компоненти мають власний стабільний API, тож зміни Reka не
     виходять назовні.
   - `KField` пишемо самі, без Alpha-`Field`.
   - Від `Drawer` можна відмовитися на користь `KSheet` знизу.
2. **Reka UI 3.0 уже в альфі.** Після стабільного релізу буде мажорна
   міграція, і ізоляція за нашим API знову її локалізує.
3. **Дати** — найскладніший компонент: локаль, часові пояси, ручний ввід.
   Reka використовує `@internationalized/date`. Його значення (`CalendarDate`)
   на межі нашого API варто конвертувати в рядок ISO `YYYY-MM-DD`, щоб
   застосунки не залежали від цієї бібліотеки.
4. **DataTable** — найбільший компонент і найбільше рішень. Його варто
   специфікувати й реалізувати останнім, коли стануть стабільними Table,
   Checkbox, Pagination, DropdownMenu й Popover.

## 6. Порядок реалізації

Без поділу на релізи (увесь каталог іде в перший реліз), але в порядку
залежностей:

1. **Фундамент:** токени, базові стилі, `KConfigProvider`, `useTheme`,
   `KIcon`, `KVisuallyHidden`, форматери.
2. **Примітивні:** `KButton`, `KIconButton`, `KLink`, `KSpinner`, `KBadge`,
   `KSeparator`, `KKbd`, `KCard`, `KSkeleton`, `KAvatar`.
3. **Форми:** `KField`, `KLabel`, `KInput`, `KTextarea`, `KCheckbox`,
   `KCheckboxGroup`, `KRadioGroup`, `KSwitch`, `KSelect`, `KNumberField`,
   `KPinInput`, `KSearchInput`, `KToggle`, `KToggleGroup`, `KButtonGroup`.
4. **Оверлеї й відгук:** `KTooltip`, `KPopover`, `KDropdownMenu`,
   `KDialog`, `KAlertDialog`, `KSheet`, `KDrawer`, `KToast`,
   `KAlert`, `KProgress`, `KEmptyState`, `KCopyButton`.
5. **Складні поля:** `KCombobox`, `KTagsInput`, `KDatePicker`,
   `KDateRangePicker`, `KFileUpload`.
6. **Доменні:** `KPhoneInput`, `KTrackingNumberInput`, `KTrackingNumber`,
   `KParcelStatus`, `KTimeline`, `KDescriptionList`.
7. **Навігація:** `KTabs`, `KBreadcrumbs`, `KPagination`, `KStepper`,
   `KAccordion`, `KCollapsible`, `KSidebar`, `KAppShell`,
   `KCommandPalette`.
8. **Дані:** `KTable`, `KDataTable`.
